::AuditImpact{metric="lcp"}

Lighthouse 13 makes LCP work more direct. Its Insights show whether time is lost waiting for the HTML, discovering the LCP resource, downloading it, or rendering the element. Start with that breakdown. Browser features such as Priority Hints, Early Hints, and Speculation Rules help only when they address the slow phase.

::InteractiveLcpTimeline

In [Lighthouse 13](https://github.com/GoogleChrome/lighthouse/releases/tag/v13.0.0), several legacy performance audits gave way to the consolidated **Insights** model. The browser still needs the same fundamentals: fast HTML, an LCP resource discoverable in that HTML, enough network priority, and little delay between download and paint.

This guide starts with those fundamentals, then covers newer options for specific bottlenecks.

## Priority Hints are baseline

Use `fetchpriority="high"` when an image is the likely LCP element and the browser would otherwise discover or prioritize it too late. [Priority Hints](https://web.dev/articles/fetch-priority) adjust a browser's initial priority; they do not bypass render-blocking work or make an undiscovered resource download.

```html
<img
  src="/hero.avif"
  fetchpriority="high"
  decoding="async"
  width="1200"
  height="600"
  alt="Hero"
>
```

:::tip
Avoid marking several images as high priority. They compete with each other and with other critical resources. Confirm the LCP candidate in Lighthouse or field attribution first.
:::

Use `fetchpriority="low"` sparingly on non-critical images that would otherwise compete with the LCP resource. Below-the-fold images should normally use `loading="lazy"` as well.

```html
<img src="/carousel-2.avif" fetchpriority="low" loading="lazy" alt="">
<img src="/carousel-3.avif" fetchpriority="low" loading="lazy" alt="">
```

Audit with the [LCP Finder tool](/tools/lcp-finder) to confirm which element browsers pick.

## Speculation Rules prerendering

[Speculation Rules](https://developer.chrome.com/docs/web-platform/prerender-pages) can prerender a likely next page before the user clicks. They improve a subsequent navigation, not the current page's LCP, and they consume bandwidth and memory. Use them only when navigation intent is predictable.

```html
<script type="speculationrules">
{
  "prerender": [{
    "where": {
      "and": [
        { "href_matches": "/*" },
        { "not": { "href_matches": "/logout" } },
        { "not": { "selector_matches": "[data-no-prerender]" } }
      ]
    },
    "eagerness": "moderate"
  }]
}
</script>
```

Choose eagerness from the cost of a false prediction:

* **`immediate`**: Prerenders as soon as the browser parses the rule.
* **`eager`**: Triggers on "hint of intent," such as scrolling the link into the viewport.
* **`moderate`**: Waits for hover (typically 200ms) or pointer proximity.
* **`conservative`**: Waits for `pointerdown`.

Start with `moderate` or `conservative`, then measure hit rate and resource cost. Browsers can reject or limit prerenders, so the destination must remain fast without them.

:::warning
Exclude logout, cart mutations, and tracking pixels. Anything with side effects needs `data-no-prerender`.
:::

## Lighthouse 13 Insights panel

[Lighthouse 13](https://developer.chrome.com/docs/lighthouse/overview) consolidated legacy audits into three primary LCP-specific insights:

::LighthouseDevtoolsMockup

**LCP request discovery (`lcp-discovery-insight`).** Replaces the old `lcp-lazy-loaded` and `prioritize-lcp-image` audits. It identifies LCP images missing from the initial HTML or marked with `loading="lazy"`. Fix by putting the image tag in the server HTML or using a `<link rel="preload">`{lang="html"} hint.

**LCP render delay (`lcp-render-delay-insight`).** Measures the gap between resource load complete and paint. High render delay means render-blocking CSS or JavaScript, or long main thread tasks like hydration blocking the compositor.

**LCP breakdown (`lcp-phases-insight`).** Shows the four-part lifecycle: TTFB, resource load delay, resource load duration, and element render delay. Target under 10% for both load delay and render delay.

```bash
npx lighthouse https://your-site.com \
  --output=json \
  | jq '.audits["lcp-phases-insight"], .audits["lcp-discovery-insight"]'
```

## 103 Early Hints

[HTTP 103 Early Hints](https://developer.chrome.com/docs/web-platform/early-hints) can send preload directives while the origin is still preparing the final HTML response. They are most useful when TTFB is material and the hinted resource is stable across responses.

Results depend on TTFB, cache state, network conditions, and whether the browser would have found the resource early anyway. Test at your CDN or server layer, then verify the request waterfall. A `103` response that hints the wrong image can waste the bandwidth you meant to save.

:::info
Keep the hint set small. Start with the critical stylesheet and a stable LCP image. Do not hint user-specific or route-dependent resources unless the edge can choose them correctly.
:::

## View Transitions are a separate concern

[View Transitions](https://developer.chrome.com/docs/web-platform/view-transitions) can make navigation feel smoother, but they do not repair a slow resource path. Same-document transitions do not start a new document load. Cross-document transitions still need a fast destination page.

Same-document View Transitions do not reset LCP. [Cross-document View Transitions](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document), enabled via `@view-transition { navigation: auto }`, count as a new page load and start a fresh LCP measurement.

```css
@view-transition {
  navigation: auto;
}

::view-transition-old(hero),
::view-transition-new(hero) {
  animation-duration: 300ms;
}

.hero-image {
  view-transition-name: hero;
}
```

Measure transitions on low-powered devices and with `prefers-reduced-motion`. A long animation can hide progress and make a navigation feel slower even when the basic LCP value is unchanged.

## Modern image formats

AVIF and WebP can reduce transfer size, but format alone does not guarantee a faster LCP. Encode at a quality appropriate for the image, serve responsive dimensions, and compare real byte sizes. A well-sized WebP can beat an oversized AVIF.

```html
<picture>
  <source type="image/avif" srcset="/hero.avif">
  <source type="image/webp" srcset="/hero.webp">
  <img src="/hero.jpg" fetchpriority="high" alt="Hero">
</picture>
```

Generate responsive AVIF with sharp or a managed service:

```js
import sharp from 'sharp'

await sharp('hero.jpg')
  .resize(1200)
  .avif({ quality: 50, effort: 6 })
  .toFile('hero-1200.avif')
```

For bulk LCP image auditing across a site, scan with [Unlighthouse](/) which reports LCP image formats, dimensions, and byte weight per page.

## Font loading with size-adjust

[`size-adjust`, `ascent-override`, and `descent-override`](https://developer.chrome.com/blog/font-fallbacks) eliminate layout shift from font swaps while keeping text paintable immediately. This makes `font-display: optional` viable for LCP-relevant text.

```css
@font-face {
  font-family: 'Inter Fallback';
  src: local('Arial');
  size-adjust: 107%;
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}

@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: optional;
}

body {
  font-family: 'Inter', 'Inter Fallback', sans-serif;
}
```

`font-display: optional` tells the browser: if the font is not cached within 100ms, use the fallback and never swap. No FOUT, no CLS, and text contributes to LCP on first paint.

For the LCP element specifically, `font-display: swap` with a metrics-matched fallback still wins because the fallback text paints immediately. Use the [Fontaine](https://github.com/nuxt/fonts) or [Capsize](https://seek-oss.github.io/capsize/) library to generate size-adjust values automatically.

## Main thread work can delay paint

Long JavaScript tasks during startup can delay the LCP element after its resource has downloaded. Lighthouse reports this as element render delay. Remove unnecessary startup work first; split or yield only when the work must remain.

Yield to the main thread during hydration:

```js
async function hydrateWithYield(components) {
  for (const component of components) {
    await scheduler.yield()
    hydrate(component)
  }
}
```

[`scheduler.yield()`{lang="ts"}](https://developer.chrome.com/blog/use-scheduler-yield) lets a long task yield to higher-priority browser work before continuing. Check browser support and provide a fallback if your audience needs one.

Break up hydration with `scheduler.postTask()`{lang="ts"} for priority-aware scheduling:

```js
scheduler.postTask(() => hydrateAboveFold(), { priority: 'user-blocking' })
scheduler.postTask(() => hydrateInteractive(), { priority: 'user-visible' })
scheduler.postTask(() => hydrateBelowFold(), { priority: 'background' })
```

## Treat HTTP/3 as a transport improvement

[HTTP/3](https://web.dev/articles/content-delivery-networks#http3) avoids transport-level head-of-line blocking between streams and can help on lossy networks. Its effect varies by audience and hosting path. Verify that your CDN advertises it, then compare field data instead of assuming a fixed LCP saving.

```bash
curl -sI --http3 https://your-site.com | head -1
```

## Edge rendering and streaming SSR

Edge rendering can reduce distance to the server, but application work, cache misses, and origin fetches still contribute to TTFB. Measure before moving rendering. A well-cached regional origin can beat an edge function that calls a distant database.

Streaming SSR pairs naturally. Send the critical HTML for the LCP element [before data-dependent sections finish](https://web.dev/articles/client-side-rendering-of-html-and-interactivity):

```ts
// Nitro / h3 streaming
export default defineEventHandler(async (event) => {
  return new ReadableStream({
    async start(controller) {
      controller.enqueue(encoder.encode(`
        <!DOCTYPE html>
        <html><head>
          <link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
        </head><body>
          <img src="/hero.avif" fetchpriority="high" alt="Hero">
      `))

      const data = await fetchSlowData()
      controller.enqueue(encoder.encode(renderRest(data)))
      controller.enqueue(encoder.encode('</body></html>'))
      controller.close()
    },
  })
})
```

The browser receives the LCP image URL in the first flush. Resource discovery happens while the origin still fetches data for the footer.

## Nuxt 4: render the LCP element in HTML

Nuxt renders pages on the server by default. Keep the LCP element in that server-rendered HTML and choose caching or prerendering per route. Do not put the hero behind `<ClientOnly>`{lang="html"} or wait for an on-mounted fetch before rendering it.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },
    '/blog/**': { isr: 3600 },
  },
})
```

Pair route rendering with `<NuxtImg preload fetchpriority="high">`{lang="html"} when the image is the confirmed LCP candidate. Defer below-the-fold interactive components with Nuxt's lazy hydration strategies, such as `hydrate-on-visible`, to reduce startup work.

## Verify with field data

Lab tests explain a repeatable page load. [CrUX](https://developer.chrome.com/docs/crux) shows what eligible Chrome users experienced over time. Use both: field data finds the affected audience and templates, while Lighthouse helps reproduce and diagnose the loading path.

Set up Real User Monitoring with the [web-vitals library](https://github.com/GoogleChrome/web-vitals):

```js
import { onLCP } from 'web-vitals/attribution'

onLCP((metric) => {
  navigator.sendBeacon('/api/rum', JSON.stringify({
    value: metric.value,
    element: metric.attribution.element,
    url: metric.attribution.url,
    timeToFirstByte: metric.attribution.timeToFirstByte,
    resourceLoadDelay: metric.attribution.resourceLoadDelay,
    resourceLoadDuration: metric.attribution.resourceLoadDuration,
    elementRenderDelay: metric.attribution.elementRenderDelay,
  }))
}, { reportAllChanges: true })
```

The [attribution build](https://github.com/GoogleChrome/web-vitals#attribution) reports the four LCP sub-parts per user. Aggregate at the 75th percentile to match CrUX.
